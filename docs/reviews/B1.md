## Fixed in this run

1. **Core-clean only checked names.** `scripts/check_core_clean.py` matched only file and directory
   stems, so `PREFIX = "/sbis/"` in `core/src` passed. It now also scans the lines of `core/src/`
   source files for any module key as a whole word. `core/tests` is not scanned, because its
   fixtures use module names. `catalog` and `pricing` are exempt from the content scan only: the
   core's `Ref` forms (§4.1) and `catalog_refs` (§3.2) name them by design. The new test is in
   `tests/scripts/test_check_core_clean.py`. The scan found `/hello/pages` in a docstring in
   `manifest.py`, now `/shed/pages`.
2. **The CI workflow's `make` step would have failed.** `which make || apt-get update && apt-get
   install -y make` parses as `(which make || apt-get update) && apt-get install -y make`, so
   apt-get install runs every time and without sudo it fails on the runner. ubuntu-latest has make,
   so I removed the step. The workflow has not yet run on GitHub as far as this box can tell; the
   first push will show it.
3. **A module test imported another module.** `modules/hello_friend/tests/test_hello_friend.py`
   imported `modules.hello.seams.Greeter`. That breaks "modules never import each other" (MAP.md),
   and the test fails if `hello` is absent. It now uses a local stand-in that satisfies
   `GreetingV1`.
4. Nothing else in `core/` names a module.

## Is the contract enough for B2?

B2's services fall into two kinds. **Core services** (identity, audit, projects, revision counter,
units, settings storage) are core code: they register through nothing. They need a core migration
chain, and the harness already discovers one at `core/src/<pkg>/migrations/`
(`tests/harness/db.py:discover_chains`). **Registries** read what modules declare. For each:

| B2 service | reads from the manifest | enough? |
|---|---|---|
| access: facets, capabilities, access keys | `Permissions(facets, capabilities, access_keys, always_on)`; `Nav.facet`, `LinkKind.permission` already checked against declared facets | yes |
| kit shell / nav | `display_name`, `accent`, `nav` (label, path, facet, order) | yes |
| mounting routes | `routers`, mounted at `/<key>` (`describe.mount_path`) | yes; the shell decides one mount point, and the test app already uses `/<key>` |
| seam registry `seams.get(Contract)` | `SeamImpl(name, version, impl)`; the contract module is found by name (`describe.contract_module_name`) | yes. The registry maps the Protocol class to the seam name through its contract module; `hello_friend/seams.py` switches from `app.state.seams` to it (B2) |
| link registry, relations, `LinkStore` | `LinkKind(name, identity, route, label, permission)`, `Relation(from, to, resolver)` | yes |
| cards | `Card(name, route, accepts, grant)`, `cards_hosted` | yes |
| events | `On(event, subject, handler)` | yes |
| jobs, cron | `Job(fn, cron)` | yes |
| validation (readiness) | `validation` callable | yes, shape only; its signature is B2's to type |
| migrations per module | `db_schema`, `migrations`, `core_revision` | **partly.** `migrations` is a free string (`"sbis/migrations"`) that nothing reads; chains are found by directory convention instead. B1.24 settles one way |
| settings with override-with-reason | **no field** | **by design**: CONTRACT.md says settings keys arrive as a manifest field with the settings service. B2 adds the field (a core change, so a core task, not a module PR) |
| units / `Quantity` | none needed; a core type | yes |

So B2 can start. Its breakdown should include adding the `settings` field to `ModuleManifest`
(with a test and a CONTRACT.md row), and making `load_modules()` the only path from the new
`app.py` and `worker.py` roots, with a test that both roots end up with the same loaded set.
