# 0024 — Validation: one shared phase-aware engine; PM owns the project phase

**Status**: Accepted (2026-08-15 — the #897 rulings plus the same-day owner design review on PR #1086, which ruled every open question; the rulings log is [VALIDATION_ENGINE_DESIGN.md §11](../planning/VALIDATION_ENGINE_DESIGN.md)) · **Amended (2026-08-19)** — decisions 6 and 7, on validation's position relative to the process pipeline

## Context

Three modules answer "are we ready to trust this data" with three unrelated mechanisms. TIVS derives readiness rules from the registry's `ProcessInput` declarations (`tivs/readiness.py`) — code-owned, stage-blind, with an audited per-project override (`TivsReadinessOverride`). SBIS hand-writes three-state checks (`ok`/`warn`/`muted`, `sbis/validation_checks.py`) whose anchor vocabulary is data-owned per project, and *infers* stage from inventory trustworthiness to decide loud vs muted. CVS validates inline in the valuation calculation: an unresolved reference poisons the value and appends a flag, with no severity model and no project rollup. Three mechanisms, three notions of when a rule applies — the rule of three, satisfied.

The requirement is stage-dependence, not polish (owner, 2026-08-07, #897): a null flag mid-survey is the honest "not inspected yet"; the same null at final valuation is a defect. Measured on 26-150: 23 of 562 valued turnouts carried complete heater data under a NULL `has_heater`, so the valuation gate never fired and 47 heaters would have silently priced at nothing — invisible to every existing report — while the same rule, enforced absolutely, would have been pure noise during the survey those rows were in.

Shipping #946 phases 4a/4b sharpened it (2026-08-15): requiredness is **basis-dependent** (`sign_posts` is consumed on 26-150 but never on 25-320, whose cost layer overrides the quantity basis onto `signs_ens` — a static `required=True` meant 429 false gaps on a delivered project), and hand-maintained requiredness **drifts** (4b's derail key narrowing forced a hand-edit of `drl_type`'s `ProcessInput` in a second place). The rule must derive from what the project's *effective* declaration actually consumes.

Owner rulings on #897 (2026-08-15) settled the shape; this ADR records them with their consequences. The 2026-08-07 direction (one JSON rule home with lock flags) is superseded in storage but not intent: the lock survives as a rule attribute; the JSON transcription is replaced by derivation from declarations.

## Decision

1. **One shared engine, platform-owned.** `platform_core.validation` owns rule registration (a manifest-declared provider per module, wired in the composition root — the ADR 0019 pattern), the result shape (`RuleDef` / `Finding` / `ModuleReport`), severity-by-phase semantics (`info` / `warning` / `blocking` resolved from a rule's phase → severity `bite` map), and the aggregate sign-off surface (built 2026-08-16 — the project-home readiness card and `/p/{code}/readiness`, which report and store nothing; *amended 2026-09-13, #1745*: the card left the project home, because every provider walking the project made the home slow even loaded lazily, and its summary is now the readiness page's Overview tab beside one tab per module). Modules own their rule **code**, their vocabularies (SBIS anchors stay data-owned), and their surfaces — the engine is the reporting and aggregation contract, not a rewrite of the three walks.
2. **An explicit project phase exists — `survey` → `costing` → `valuation` → `delivered` — and the PM module owns it.** The terminal `delivered` phase was added in the design review; it carries the same severity as `valuation` (a shipped marker, never a new severity regime). Set deliberately by PM-write users, audited in-transaction (the `platform_core.projects.lifecycle` precedent), stored in the `pm` schema, and read by other modules only through a seam (ADR 0002 / the ADR 0010 `sbis_seam` shape — never a cross-schema ORM join). It is data maturity, deliberately distinct from ADR 0014's business `lifecycle_stage` (`analysis` alone spans costing and valuation; no lossless mapping exists). Unset is legal: SBIS's trustworthiness inference becomes the **fallback** for unset phases, not the mechanism; TIVS falls back to today's stage-blind semantics.
3. **Rule existence derives from declarations; only severity and phase threshold are configurable — never on/off.** Derived rules (calculator inputs, effective cost-declaration consumption, equipment gates) are generated, not transcribed, so identity changes update the rule set atomically. Rules whose subject feeds a number are **locked**: visible everywhere, never editable, severity floored at `blocking` for the `valuation` phase. `TivsReadinessOverride` survives unchanged as the audited, field-grain, per-project escape hatch (locked rules refuse it).
4. **The ADR 0009 boundary holds: a calculation decides what a number is; validation decides whether we trust it.** Rules never gate or mutate a run (the valuation run's skip attribution never reads overrides — preserved); severity and phase config change what is *reported*, never what is *computed*; rule conditions are code, so no project can redefine a rule into vacuity; authored predicates, where needed, use the closed forms only.
5. **#946 phase 5 ships inside this design** as the engine's first TIVS plug-in — consumption rules derived from the per-project effective declaration — not ahead of it (owner ruling: no code before the design).
6. **Amended 2026-08-19 (#1161) — validation evaluates source data; a process transformation shapes which rules *apply*, never which records are *seen*.** Owner: *"if the process masks the validation, then are we truly validating the source data?"* Measured, only one stage was inverted. `frames.prepared()` is `filter → coalesce → reshape → enrich → derive`, and the readiness walk consumes the output — but `coalesce` deliberately lands an explicit `None` for an all-null slot family *"so readiness reports the canonical gap"*, and `enrich`/`derive` run first precisely to **expose** gaps (a gated end nothing resolves "reads `None` here and is reported — never a silent zero"). Those three legitimately precede the walk and stay. **Row selection does not**: a record removed by a link's `row_filters` cannot be reached by any rule, which is why `include IS NULL` is unwritable today (#1040) and why an asset moving `include` 0 → 1 has no rule that notices. A rule's scope therefore belongs **in its own predicate** — `include = 1` is stated by the rules that mean it — and `row_filters` become an input a rule may read (`failing_filters` already computes exactly this, #902) rather than a gate on visibility. The calculation's filters are unchanged; what changes is that validation no longer inherits them by construction.
7. **Amended 2026-08-19 (#1161) — a rule states what it asserts, that statement is recorded, and it is rendered before new rules are authored.** `RuleDef` carries identity and bite but **no predicate**, so what makes a rule fire lives only in the code that produced it and nothing can show it. It gains a recorded subject (asset type / field) and its **authored** condition — the clause the rule itself asserts; derived rules populate that from the declaration that produced them, authored rules state it. The **effective** predicate is composed at render time from the authored clause plus every inherited one, each attributed to its origin, and is not stored — storing it would let it drift from the pipeline it describes, which is the failure this amendment exists to end. A debug surface renders the catalog — owner ruling: **build the surface first**, because a definition that is not recorded cannot be displayed, which makes the surface the forcing function for explicitness rather than a report about it. **What is rendered is the EFFECTIVE predicate**: every condition that determines whether the rule fires, including the ones it inherited rather than authored. Owner, 2026-08-19: *"while a rule might be inherited from a process (valuation), it should be humanly readable as what defines it — so if valuation filters on `include = 1`, then any inherited rule should include that in the human-readable rule."* Inheritance is a legitimate mechanism; opacity is not. So `xing.surf_type2` reads as `include = 1 AND num_tracks >= 2 AND surf_type2 IS NULL` with each clause attributed to its origin (link filter, `when` gate, the rule itself) — which is renderable **today**, before decision 6 moves any evaluation, and is what makes the surface worth building first rather than last. This also decouples the **vocabulary**: `ProcessInput` is *"the calculation-dictionary seed"* and its `required` means "a NULL blocks this process", so deriving every rule from it means **only what is valued can be validated**. A rule may reference any *landed* field. The worked pair, which is the acceptance test: `xing.surf_type2` must not flag when `num_tracks = 1` (already correct — `when=(RowFilter("num_tracks", ge=i),)`), while `wayside_det_ontrk.ded_type_det` must flag when `has_ded = 1 AND include = 1` — inexpressible today, because those fields ride the JSONB passthrough and nothing calc-consumes them.

The full contract, the phase mechanics, the rule taxonomy (presence / contradiction / cardinality / consumption / consistency / reference / configuration — cardinality explicitly sequenced behind COST_TABLES.md §per_slot), the per-module migration stages, and the design-review rulings log (all seven open questions ruled 2026-08-15 — four phases, per-project config in the first slices, sign-off on the project home, engine + #946 phase 5 as slice 1, SBIS before CVS) are in [VALIDATION_ENGINE_DESIGN.md](../planning/VALIDATION_ENGINE_DESIGN.md).

Stages A–G all shipped 2026-08-15/16. Two taxonomy classes did **not** ship as designed, both on evidence rather than schedule: **contradiction was dropped** (owner ruling 2026-08-16 — production encodes "explicitly absent" three undeclared ways, so the derivable rule fires 421 false positives on today's data and the honest one needs a vocabulary the declarations do not carry), and **cardinality still waits** on COST_TABLES.md §per_slot. **Presence shipped narrowed** to the gates no other derived rule already blocks on — two rules, not eight, because three of the four equipment gates are already locked consumption predicates. The re-measurement is §2.1.1 of the planning doc and the rulings are §11.2.

## Consequences

- The three modules keep their surfaces and their rule code; what they gain is one severity vocabulary, one phase source, and membership in a project-level sign-off view — the thing someone about to lock a valuation actually wants.
- The `sign_posts` / `drl_type` / `flex_attr1` class of drift (a requiredness fact maintained by hand beside the declaration that already knows it) ends by construction for every derived rule.
- SBIS stops being the only stage-aware module and stops inferring where a phase is set; TIVS stops being stage-blind; CVS gains a rollup it never had. The strict calculation filters (CVS `include == 1`, TIVS row filters) are calculation policy and remain untouched **as calculation policy** — *amended 2026-08-19*: they no longer decide what validation may evaluate, which is decision 6. The distinction matters because the sentence as first written was read as settling both.
- PM grows one table, one workspace control, and one seam — an addition under ADR 0014, not a redesign; the phase is auditable history, not a computed guess.
- A new module gets validation by writing rules against the engine instead of inventing a fourth mechanism.
- Accepted friction, deliberately: changing a rule's *condition* requires a PR and deploy, exactly as ADR 0009 accepts for calculations — that friction is the review control; only bite (severity/threshold) is ever data.
- *Amended 2026-08-19*: the ADR 0009 boundary in decision 4 gains its missing half. "A calculation decides what a number is; validation decides whether we trust it" only holds if validation can speak about data the calculation ignores — otherwise trust is scoped to whatever happens to be priced. Decision 7 is what makes the sentence true.
- *Amended 2026-08-19*: rules become reviewable by reading them rather than by tracing the pipeline, and the two amendments are **independently shippable in this order** — rendering the effective predicate (decision 7) needs no change to what any rule evaluates, and is the evidence base for deciding decision 6's scope change. The cost of the old shape was measured on 2026-08-19 — establishing whether TIVS suppressed findings on excluded assets required reading four modules and running the pipeline, and a first answer drawn from a source grep was wrong. A rendered predicate answers that in one screen.
- *Amended 2026-08-19*: accepted risk — surfacing rules over unfiltered rows can raise findings on records nobody intends to value. That is why decision 6 puts scope **in the predicate**: a rule that means `include = 1` says so, and #1157 carries the policy (excluded assets are informational; valuation-grade rules stay silent on them; `include IS NULL` is always flagged).
